# Incident writeup — deliberate worker-crash drill (2026-08-08)

This is a first-person account of a planned failure drill: I stopped the worker
on the running stack and watched how the platform behaved, how it told me what
had broken, and how it recovered. All timestamps below are UTC and come from
`evidence/05-observability/alert-sink.log`; two "worker stopped/restarted"
moments are derived from the alert timings and are marked as such.

## What I did

I stopped the `worker` container while the rest of the stack (api, postgres,
redis, prometheus, alertmanager, grafana) kept running. I did not stop anything
else. The `WorkerDown` rule fires on `up{job="worker"} == 0` sustained **for 1
minute** and started firing at **20:25:24Z**, so scraping of `worker:9100` had
been failing since roughly **20:24:24Z** — that is when the worker effectively
went away.

## What the user experienced: nothing

This is the part I find most interesting. Stopping the worker had **no effect on
writes**. `POST /events` persists the event and enqueues a job, then returns
without waiting for processing, so with the worker gone the API kept accepting
events and returning **201 Created** exactly as before. `/ready` stayed 200 —
its dependencies are Postgres and Redis, both of which were healthy. From a
client's point of view the platform was fully up. The failure was completely
invisible at the write path; events simply accumulated at `status='received'`
with nothing draining them. A failure you cannot see at the front door is
precisely the kind that runs for hours before anyone notices — which is the
whole reason the lag telemetry exists.

## What the telemetry showed

The system surfaced the problem on its own, in two stages:

| Time (UTC) | Event |
|---|---|
| ~20:24:24 | worker stopped (derived from `up==0` for 1m before the alert start) |
| 20:25:24 | `WorkerDown` begins firing (`startsAt`); delivered to alert-sink at **20:25:34** |
| ~20:26:09 | oldest-unprocessed age crosses 120s (derived: 2m before the lag alert start) |
| 20:28:09 | `EventProcessingLag` begins firing (`startsAt`); delivered at **20:28:19**, reporting the oldest unprocessed event as **4m 1s** old |
| ~just before 20:29:09 | worker restarted (derived: both alerts resolve at this `endsAt`) |
| 20:29:09 | both alerts resolve; the lag alert's resolve payload reports the oldest event at its peak of **4m 46s**; `EventProcessingLag` resolved delivered at **20:29:09**, `WorkerDown` resolved at **20:29:14** |

`WorkerDown` (critical, `instance=worker:9100`) fired first because absence of
scrapes is detectable in one minute. `EventProcessingLag` (critical,
`instance=api:8000`) followed about three minutes later, once the oldest
unprocessed event had been over the 120s threshold for a sustained two minutes.
Both firing and both resolved payloads landed in `alert-sink.log`, which is what
makes the alerting provable end to end rather than merely configured.

## How I identified the component

I did not need to guess. Dashboard **row 1 ("Is it up?")** showed the worker
**DOWN** while api, postgres, and redis all stayed **UP** — see
`evidence/05-observability/dashboard-worker-down.jpeg`. That immediately rules
out the ingestion path and the datastores. Dashboard **row 3 ("Is processing
keeping up?")** showed the oldest-unprocessed-age line climbing steadily past its
120s threshold while **row 2 ("Is it failing?")** showed the API healthy with no
error-rate spike — see `evidence/05-observability/dashboard-lag-climbing.jpeg`.
Reads and writes healthy, but the backlog growing, points in exactly one
direction: the failure is **downstream of ingestion**, in the component that
drains the queue. `up{job="worker"} == 0` then named that component precisely.
The diagnosis path built into the `EventProcessingLag` annotation — "check
`up{job="worker"}`; if 0 the worker is down" — is the same path I actually
walked.

## Recovery

I restarted the worker. It reconnected, Prometheus scraped it again, and it
began draining the backlog immediately. Recovery was fast enough that both
alerts cleared in the **same evaluation at 20:29:09Z**: `up{job="worker"}`
returned to 1 and the oldest-unprocessed age fell back under 120s together. The
lag metric's peak of **4m 46s** in the resolve payload is essentially the age of
the oldest event at the instant the worker came back — after that it dropped
straight down as the queued events were processed. Dashboard row 3 returning to
baseline is captured in `evidence/05-observability/dashboard-recovered.webp`.
Total worker outage was roughly four and a half minutes (~20:24:24Z to just
before 20:29:09Z).

## What would reduce likelihood or impact

- **Run at least two worker replicas.** With `replicas >= 2` a single worker
  dying degrades throughput instead of halting processing entirely.
- **A restart policy / liveness probe.** The compose services already use
  `restart: unless-stopped`; on Kubernetes a liveness probe would restart a
  hung (not just exited) worker automatically.
- **The lag alert — already in place.** `EventProcessingLag` is the alert that
  makes this failure visible despite the API looking healthy; this drill is its
  proof.
- **A dead-letter queue** for jobs that fail repeatedly, so one poison event
  cannot wedge the worker and masquerade as an outage.
- **Autoscale on queue depth.** `dropme_queue_depth` is already exported;
  scaling workers on it would drain a backlog faster and absorb bursts.

The single most valuable control here was the lag metric: every other signal
(request rate, error rate, `/ready`) said the system was fine. Only
`dropme_oldest_unprocessed_event_age_seconds` told the truth.
